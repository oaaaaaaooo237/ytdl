# Android 1.0.1 任务页与下载进度设计

## 目标

改进下载进度信息，合并队列与历史入口，支持后续任务等待和取消任务重试；把格式选择完整合并到下载页，下载得到的主文件统一使用解析出的媒体标题命名，并把用户可见版本升级为 1.0.1。历史数据库结构保持不变。

## 采用方案

采用“组合页面”方案：保留现有运行中队列卡片和历史卡片，在同一个 `tasks` 路由中按任务状态组合展示。

- 有正在运行的任务时，页面顶部显示现有队列卡片、阶段条和取消操作。
- 下载完成、失败或取消后，不再保留一张终态队列卡片；刷新 Room 历史记录，按现有历史卡片展示。
- 历史搜索、筛选、打开、分享、再次下载和删除行为保持不变。
- 底部导航最终改成“下载 / 任务 / 设置”三项。

## 格式选择合并到下载页

- 独立“格式”页面和底部入口删除。格式选项只在地址分析成功后出现，放在下载类型与保存位置之间。
- 下载类型按“视频+音频 / 视频 / 音频”排列。解析结果不支持某种类型时，对应按钮置灰且不可点击。
- “视频+音频”和“视频”显示当前真实提供的分辨率、编码、帧率和容器，选择仍映射到精确格式 ID。
- “音频”显示真实音频格式和容器；视频分辨率、帧率、视频编码显示为灰色不可用项，不生成任何视频选项。
- 历史中的“再次下载”完成重新分析后直接回到下载页，并恢复仍有效的上次格式选择，不再进入已经删除的格式页。

## 顺序下载队列

- 当前任务下载时，用户仍可分析另一条地址并把它加入等待队列。
- 前台服务使用单线程执行器，严格按加入顺序执行；无论队列中有多少任务，同时都只有一个任务访问网络、处理文件或导出。
- `DownloadCoordinator` 分别维护当前任务和等待任务快照，任务页顶部先显示当前任务，再显示状态为“等待中”的任务。
- 当前任务完成、失败或取消后，下一条等待任务自动开始；取消当前任务不会清空后面的等待任务。
- 1.0.1 的等待队列保存在应用进程内，不新增数据库表；前台下载服务运行期间队列有效。系统强制结束应用进程后，尚未开始的任务不会自动恢复。

## 取消任务重试

- 失败和取消任务都保存不含 cookies 的加密重试草稿。
- 历史卡片有可用重试草稿时显示“再次下载”；点击后仍先重新分析原地址，再由用户确认格式和授权。
- 已完成任务不保存重试草稿，删除历史记录时同步删除对应草稿。

没有采用以下方案：

1. 仅把“队列”和“历史”两个按钮指向同一页面。它仍会保留五个入口，不符合要求。
2. 把运行中任务和历史记录改造成同一个全新卡片模型。该方案会扩大改动范围，并增加对重试、打开、分享和删除行为的回归风险。

## 下载进度

进度条下方固定显示一行：

`速度 3.2 MB/s · 已下载 12.4 MB · 总计 48.0 MB`

- 速度使用 yt-dlp 当前进度回调实时更新。
- 已下载大小使用当前下载阶段累计字节数实时更新。
- 总大小在当前阶段第一次获得有效值后固定，后续回调即使给出不同估算值也不改变。
- 视频+音频任务从视频阶段进入音频阶段时，清空上一阶段的速度、已下载和总大小，再使用音频阶段的新数据。
- 无法取得速度或总大小时显示 `--` 或 `未知`，不制造估算值。

## 文案精简

- 删除前台中的“媒体文件”表述，改成“文件”或直接说明保存结果。
- 历史卡片第二行保留有意义的媒体类型（“视频+音频 / 视频 / 仅视频 / 仅音频”）、主文件名、完成时间，以及安全处理后的失败原因。
- 不再在第二行显示详细格式、分辨率、网站来源 `web/youtube/...`、输出类型和完整文件路径。
- 分辨率与编码继续显示在卡片右下角徽标中。
- 没有有意义的第二行内容时不渲染占位文字。

## 主文件命名

- 直接下载的视频、仅视频、仅音频，以及自动合并后的视频主文件，都默认使用分析结果中的媒体标题作为主文件名。
- 保留实际输出格式对应的扩展名；自动合并结果使用 `.mp4`。
- 文件名中的 Windows 非法字符、控制字符和末尾空格或句点会被安全替换；空标题使用“未命名媒体”。
- 独立视频流、音频流等中间文件放在任务目录的 `.parts` 子目录，不作为用户最终文件展示；合并成功或失败后仍按现有规则清理。

## 底部导航尺寸

三个入口平均分配宽度。图标保持 20dp，文字使用更醒目的字号和字重，同时保留系统手势区安全距离与至少 48dp 的触控高度。

## 验收标准

1. 自动化测试证明速度和已下载大小随回调变化，总大小在同一阶段保持不变，切换阶段后可更新。
2. 自动化测试证明两个以上任务严格按 FIFO 顺序切换，且任一时刻只有一个任务处于执行状态。
3. 自动化测试证明取消任务保存重试草稿并显示“再次下载”。
4. 自动化测试证明底部只有“下载 / 任务 / 设置”三个入口，且不存在独立“格式”入口。
5. 自动化测试证明历史第二行保留媒体类型和主文件名，但不含分辨率、来源、输出类型、“媒体文件”或完整文件路径。
6. 自动化测试证明直接下载与自动合并得到的主文件都使用解析出的媒体标题命名，并保留正确扩展名。
7. API 37 可见模拟器真实操作验证 YouTube、Pornhub、Eporner 地址分析。
8. API 37 可见模拟器完成一次视频+音频下载和一次单视频下载，并验证文件名、第二条任务先等待后自动开始；不测试字幕。
9. Python、Android 单测、debug/release 构建及必要仪器测试通过后，生成 1.0.1 APK，提交并推送当前分支。
10. 自动化测试证明分析后的格式选项位于下载页；“视频+音频 / 视频 / 音频”按解析结果启用或置灰。
11. 音频模式不显示可选的视频分辨率或编码，视频相关项目明确置灰，历史“再次下载”回到下载页。

## 实现结果（2026-07-15）

问题 1 至 7 已在 API37 模拟器范围实现并验证；问题 8 按本节继续实施和复核。小米 14 最终真机复核仍属于主计划 M10/D2，不在本设计的模拟器发布结论内。
