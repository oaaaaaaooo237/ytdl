# Android 1.0.1 历史操作同排与连续分析设计

## 目标

缩短任务页每张历史卡片的高度，并保证连续分析多个不同地址时，界面始终显示最后一次发起分析的地址及其对应结果。

## 历史卡片操作布局

- 完成记录把“打开 / 分享 / 删除”放在同一个操作区。
- 可重试的失败或取消记录把“再次下载 / 删除”放在同一个操作区。
- 删除按钮继续使用现有红色、圆角、图标和尺寸，不改成普通文字按钮。
- 操作区沿用 `FlowRow`。在当前标准手机宽度和默认字体下保持一行；只有系统字体显著放大、确实无法容纳时才允许自动换行，避免按钮被截断或重叠。
- 删除确认框、删除历史但不删除成品文件、打开、分享和再次下载的行为均不改变。

考虑过但不采用：

1. 固定 `Row` 强制永不换行：默认宽度下简单，但大字体会溢出，不采用。
2. 把删除按钮固定到操作区最右侧：会和右侧状态、编码、分辨率徽标争抢宽度，不采用。

## 连续分析结果归属

- 每次点击“分析”都取得输入框当前的完整地址并生成递增请求编号。
- 只有仍是最新编号的分析结果可以写回标题、时长、缩略图和格式列表。
- 前一次分析即使更晚返回，也只能被丢弃，不得覆盖后一次地址或后一次结果。
- 地址实际发生变化时继续清空旧分析结果；地址输入框因重新挂载而回传相同文本时不清空结果。
- 不在日志、历史、错误信息或测试报告中输出完整地址、cookies、IP 或原始异常。

## 验证

1. Compose 回归测试验证完成卡片的三个操作按钮处于同一操作区，可重试卡片的两个按钮也处于同一操作区；删除按钮仍使用红色强调。
2. JVM 测试用受控分析提供器制造“第一次请求后返回、第二次请求先返回”，断言最终只显示第二次结果。
3. 顺序运行 Android 聚焦单测、全量单测、debug/release/debugAndroidTest 构建。
4. 提交、推送并生成新的 1.0.1 APK 归档后，在唯一可见 API37 模拟器中检查历史卡片高度和按钮同排。
5. 使用用户给出的四个 Pornhub 地址逐个进行前台真实分析。每个地址都通过可见 Gboard 输入，核对输入框后再点击分析；记录每次标题、时长或格式摘要发生对应变化，只分析，不下载。

## 完成边界

- 四次真实分析全部对应当前输入地址，才可宣称连续分析通过。
- 如果任一次仍显示前一个地址的结果，修复后重新构建、重新发布，并从第一个地址开始完整复测。
- API37 模拟器通过不替代小米 14 最终真机验收；release APK 在配置正式密钥前仍保持未签名。
